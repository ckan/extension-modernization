# Code Review Guidelines: Anti-Patterns and Modern CKAN Solutions

Use the following guidelines when performing code reviews for CKAN extensions. For detailed explanations, refer to the online documentation at https://extension-modernization.readthedocs.io/en/latest/.

## Code Quality & Architecture

### Plugin Registrations
When you spot manual helper, action, auth, or validator registrations (such as get_actions, get_auth_functions, get_validators, or get_helpers) in `plugin.py`, you should suggest the author use `@tk.blanket` decorators for automatic discovery instead of manual registration methods.

### Logic and Action Invocations
When you spot imported action, auth, or helper functions being invoked directly, you should suggest the author use `tk.get_action("action_name")(context, data)` or `tk.check_access("auth_name", context, data)` instead of direct function imports.

### Nested Context Isolation
When you spot a parent action's `context` being passed directly to nested `get_action` or `check_access` calls, you should suggest the author use `child_context = tk.fresh_context(context)` to isolate the sub-call instead of passing the contaminated parent context.

### Database Query Standards
When you spot legacy SQLAlchemy query patterns (such as `Session.query` or `model.Session.query`), you should suggest the author use modern SQLAlchemy v2 `select()` and `session.scalar()` or `session.scalars()` instead of legacy query APIs.

### Serialization and Dictization
When you spot model dictization or serialization methods retrieving parameters from the `context` dictionary, you should suggest the author define them as keyword-only parameters (e.g., `*, include_details: bool = False`) instead of relying on context variables.

### Template Helper Queries
When you spot database queries (such as SQLAlchemy `Session` operations) inside a template helper function, you should suggest the author query catalog indexes using Solr search actions (like `package_search` or `package_show`) instead of performing direct database operations.

## Security & Authorization

### Action Access Checks
When you spot a custom action that does not execute `tk.check_access` at the very beginning of the function body, you should suggest the author add a permission check instead of executing logic without authorization controls.

### Auth Access Decorators
When you spot a custom authorization function that lacks access decorators, you should suggest the author decorate the function with either `@tk.auth_disallow_anonymous_access` or `@tk.auth_allow_anonymous_access` instead of leaving access controls implicit.

### Blinker Signal Mutability
When you spot a Blinker signal subscriber that attempts to modify `data_dict` properties, raise validation exceptions, or return HTTP responses, you should suggest the author use a CKAN Interface instead of using a read-only signal observer.

### Blinker Signal Connection
When you spot a direct Blinker signal connection (such as `signals.connect` or `signals.action_succeeded.connect`), you should suggest the author implement the `p.ISignal` interface with `get_signal_subscriptions()` instead of connecting to signals directly.

## Testing Standards

### Action Test Isolation
When you spot database state initialization in tests done via creation actions (like `call_action("package_create")`), you should suggest the author utilize registered pytest-factoryboy factories (such as `package_factory()`) instead of executing creation actions in setup loops.

### Mocking Logic Internals
When you spot tests monkeypatching or overriding `get_action` or other logic internals to assert flow delegation, you should suggest the author use a black-box testing strategy (verifying resulting database records or exception states) instead of mocking logic internals.

### Test Fixture Declarations
When you spot `clean_db` or `with_plugins` fixtures being passed as function arguments in test suites, you should suggest the author register them using `@pytest.mark.usefixtures("clean_db", "with_plugins")` at the class or module level instead of injecting them as parameters.

### Test Client Logins
When you spot test requests requiring authentication without a login session, you should suggest the author authenticate the Flask test client using `app.set_session_user(user)` instead of manually modifying cookies.

### Playwright Test Scope Mismatch
When you spot backend API logic, action parameter validation, or standard page redirects being tested with Playwright, you should suggest the author write standard pytest-ckan tests instead of spinning up browser E2E tests.

### Missing E2E Tests for Complex UI
When you spot complex interactive frontend components (such as Leaflet maps, charting widgets, or multi-step wizard forms) lacking E2E tests, you should suggest the author write Playwright tests to cover browser behavior instead of relying solely on backend unit tests.

## Docker Environment

### Docker Plugin Variables
When you spot only one of `CKAN_PLUGINS` or `CKAN__PLUGINS` defined in `.env` or compose configurations, you should suggest the author specify both variables in unison instead of omitting one.

# Review topics to exclude

## Avoid providing feedback on formatting
When you find code formatting discrepancies (such as whitespace, indentation, or imports ordering), you should avoid leaving any suggestions because these are handled by linting tools.
